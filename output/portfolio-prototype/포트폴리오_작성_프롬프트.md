## 내용 구성

프로젝트 전체는 ‘게임 소개 한 문장 → 본인 담당 범위 → 핵심 구현 2~3개 → 실제 시연·소스 링크’로 구성하세요. 프로젝트에 존재하는 모든 기능을 나열하지 마세요. 문장만 읽어도 무엇을 구현했는지 이해되어야 하며, 코드는 그 내용을 확인하는 보조 근거여야 합니다.

각 기능의 본문을 다음 흐름으로 이어지는 짧은 문단으로 작성하세요. 아래 항목을 반드시 소제목 다섯 개로 쪼갤 필요는 없습니다.

1. 목표: 어떤 게임 동작을 구현하려 했는가?
2. 정보 정의: 그 동작에 필요한 값·상태·자료구조는 무엇인가?
3. 처리 연결: 입력을 받은 뒤 어떤 데이터를 어디로 전달하고, 어디에 반영했는가?
4. 핵심 판단: 실제 자료에서 확인되는 선택이나 문제 해결을 한 가지 설명한다.
5. 결과: 게임에서 어떤 동작이 가능해졌는가? 실행 검증이나 수치는 증거가 있을 때만 쓴다.

처리 흐름의 순서와 실제 개발 이력은 구분하세요. 코드만 읽고 ‘처음에는 A를 시도했지만 실패해 B로 바꿨다’ 같은 과거 경험을 만들지 마세요. 선택 이유가 기록되어 있지 않으면 코드가 수행하는 역할을 설명하세요.

구조 설명은 관련 객체·컴포넌트·서버·클라이언트가 각각 어떤 정보를 소유하고 전달하는지 드러내세요. 실제 코드가 한 클래스에 모여 있다면 책임이 잘 분리된 설계라고 꾸미지 마세요. 자료구조를 사용했다는 사실만으로 확장성이나 성능이 개선됐다고 단정하지 마세요.

## 코드와 그림 사용

- 본문이 먼저이고, 코드는 본문에서 설명한 구현을 확인할 수 있는 근거입니다.
- 기능마다 핵심 코드 한 개를 우선 선택하세요. 구조체와 적용 코드가 함께 필요할 때만 두 개까지 사용하세요.
- 코드 블록은 원칙적으로 8~15줄로 제한하세요. 전체 함수가 더 짧으면 그대로 사용하세요.
- 실제 소스를 발췌하고 생략한 부분을 표시하세요. 설명용으로 재작성한 경우 반드시 ‘설명용 의사코드’라고 구분하세요.
- 변수 대입이나 조건문을 줄마다 해설하지 마세요. 본문의 정보 정의·송수신·상태 적용을 뒷받침하는 코드인지 확인하세요.
- 그림은 ‘캐릭터 정보 정의 → 서버 전달 → 다른 클라이언트 수신 → 객체 상태 갱신’ 같은 처리 흐름을 3~4단계로 간단히 표현하세요.
- 코드와 그림을 크게 늘려 동일한 설명을 반복하지 마세요.

- 확인되지 않은 성능 수치, 최적화 성과, 테스트 결과, 문제 해결 경험을 만들지 마세요.
- 현재 남은 결함은 해결했다고 쓰지 말고 작성자용 검토 메모에 기록하세요.

## 문체 적용 예시 — NGP 캐릭터 동기화

다른 플레이어의 움직임을 각 클라이언트에 표시하기 위해, 먼저 캐릭터 간에 주고받을 정보를 정리했습니다. 캐릭터 ID, 위치, 이동 방향, 회전각, 팔다리 움직임 각도를 구조체에 담아 서버로 전달했습니다. 서버는 수신한 캐릭터 정보를 저장하고, 각 클라이언트에 다른 플레이어의 상태를 전달하도록 구성했습니다. 저는 전달받은 값을 각 캐릭터 객체의 위치·회전·동작에 반영하는 부분을 연결하여 캐릭터 움직임의 동기화를 구현했습니다.

본인 담당: 캐릭터 정보 송수신 및 적용. 서버 연결·스레드 구성은 팀원 담당.

보조 코드 선택: 클라이언트 main.cpp의 1060~1068행(송신할 정보 구성), 84~94행(수신 상태 적용). 두 코드 사이를 ‘캐릭터 상태 정의 → 서버 전달 → 다른 클라이언트 수신 → 객체 갱신’으로 연결해서 보여줍니다. 충돌 처리는 별도 기능으로 설명합니다.
